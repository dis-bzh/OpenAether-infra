# Reprise après sinistre — une chaîne ordonnée, de rien à une plateforme qui fonctionne

🇬🇧 [English version](disaster-recovery.md)

> Écrit pour répondre aux règles ANSSI sur un plan de reprise documenté, des objectifs de temps et un test de reprise (id d'audit F-BKP-16). Il relie les
> éléments existants dans l'ordre qui marche, et depuis 0.4.0 `task dr-restore-plan` les lance dans cet ordre ; **la chaîne dans son ensemble a été exécutée sur des clusters (un cluster jetable au lab 20, des reconstructions Scaleway au lab 28B et dans deux labs de preuve de la 0.4.1, ci-dessous), jamais sans surveillance** : le palier est
> dit pour chaque étape, et ce qu'une exécution a demandé à la main est listé ci-dessous. Les objectifs de temps sont des propositions, pas des
> mesures. Il ne revendique aucune conformité à un document ANSSI.

Lire d'abord `backup-policy.fr.md` pour ce qui est copié, et `incident-response.fr.md` si la reprise a pour cause une attaque (choisir un point de
restauration antérieur à T0, fermer d'abord la porte, renouveler après avoir restauré).

## 1. Quel sinistre

| Situation | Chemin |
|---|---|
| Un nœud perdu ou qui déraille | `rolling-replace` (`upgrade.fr.md`, « Remplacer un nœud ») : pas cette page |
| Le cluster a disparu, le provider et les buckets vont bien | sections 2 et 3, sur le même provider |
| Le provider a disparu (compte, région, le store primaire) | sections 2 et 3, en partant du réplica chez l'autre provider : `cluster/README.md`, « Cross-provider failover » |
| L'état a perdu ses secrets Talos mais les nœuds vivent | `cluster/README.md`, « Lost the Talos secrets » : pas une reconstruction |
| Seul OpenBao a perdu ses données | section 3 à partir de l'étape 5 |
| Une attaque | `incident-response.fr.md` d'abord |

## 2. Prérequis : ce qui doit déjà être hors du cluster

Si l'un manque, l'étape correspondante ne peut pas être faite ; l'objectif de reprise devient alors « reconstruire sans ces données ».

| Nécessaire | Détenu par | Perdu signifie |
|---|---|---|
| K5 (et K6 si posée) | le coffre de l'opérateur, idéalement à deux endroits | l'état, les artefacts et les snapshots sont illisibles : **pas de reprise de la PKI Talos** ; reconstruire avec une nouvelle PKI |
| Clés de stockage objet du store **survivant** (`<PU>_BACKUP_AWS_*` ou celles du primaire) et identifiants du provider | `.env.sh`, le coffre | en créer de nouvelles chez le provider ; ce ne sont les clés d'aucun secret |
| Les tfvars du cluster (`envs/<role>-<provider>.tfvars`, ignorés par git) | la machine de l'opérateur | les refaire depuis l'`.example` avec le nom du cluster, l'environnement, le `bucket_suffix`, l'endpoint et la région du réplica (`cluster/README.md`) |
| La clé de scellement OpenBao (séquestre, deux dépositaires) | `docs/admin-access.fr.md` section 1 ; apps Day 0 | **tous les secrets OpenBao et tous les snapshots raft sont perdus** |

| Le mot de passe restic (séquestre) | le coffre | les sauvegardes applicatives sont illisibles |
| Ce dépôt au tag qui a construit le cluster, et OpenAether-apps au `git_ref` qu'il épinglait | GitHub, et le clone de l'opérateur | construire depuis le tag que vous pouvez tirer ; rien ici n'est vendorisé |

### Une seule commande

`task dr-restore-plan` est le tableau ci-dessus en commande (`scripts/ops/dr-restore-plan.sh` ; elle n'ajoute aucun mécanisme, chaque étape appelle une commande qui existe). C'est un **dry-run par défaut** : elle affiche chaque étape avec les commandes de CE
cluster (ses buckets, dépôts et store), les entrées dont chaque étape a encore besoin et celles qui manquent, et ne lance rien. La lancer avec `--strict` avant le jour où on en a besoin. `--execute --confirm <cluster_name>` lance la
chaîne, un contrôle après chaque étape, et s'arrête au premier échec en disant l'étape où reprendre ; elle écrit un rapport de temps (un TSV, secondes et objectif par étape, l'horloge murale contre les 8 h) pour remplir le tableau de la section 5.

```bash
task dr-restore-plan PROVIDER=scaleway -- --from replica                         # dry-run : étapes ordonnées, commandes de ce cluster, entrées manquantes
task dr-restore-plan PROVIDER=scaleway -- --from replica --strict --seal-key-file F --restic-password-file F \
  --bao-token-file F --recovery-shares-dir D                                     # disponibilité : code 1 s'il manque une entrée
task dr-restore-plan PROVIDER=scaleway -- --from replica --seal-key-file F --restic-password-file F --bao-token-file F \
  --recovery-shares-dir D --execute --confirm <cluster_name>                     # la chaîne ; --from-step <id> reprend, --only <id,id> un sous-ensemble
```

Étapes (scénario reconstruction) : `artifacts` (1), `cluster` (2, avec `deploy_flux = false`), `seedkey` (3), `flux` (4 : `deploy_flux = true`, un second `task cluster-up` ; le tfvars précédent est gardé en `.dr-bak`), `hold` (les Kustomizations hors de la fermeture de dépendances
d'OpenBao sont suspendues, leur parent `openaether-platform` en premier, et chacune est relue comme suspendue), `generation` (la nouvelle génération d'archive CNPG, ci-dessous), `openbao` (5), `shares` (6), `resume` (7 : tout ce qui est retenu sauf `identity*`, `observability`, qui porte Grafana, et le parent `openaether-platform`), `dbs` (8), `identity` (9 : identity et observability, puis le parent `openaether-platform` en dernier, qui ré-applique le reste ; elle attend le DAG et que chaque ExternalSecret, ceux de Grafana et de Loki compris, soit prêt, sauf `services-observability/grafana-oidc`, nommé dans la sortie quand il n'est pas prêt ; `OA_DR_ES_OPTIONAL` remplace cette liste, vide elle compte tous les ExternalSecrets), `verify` (11 : `cluster-verify`, une sauvegarde de base de chaque nouvelle archive et sa copie vers le store réplica, puis un test de restauration lancé sur le cluster reconstruit). `--db-source pitr` (par défaut) récupère chaque
base CNPG depuis l'ObjectStore du store choisi (avec `--pitr-time` au besoin) dans un Cluster jetable `<nom>-dr`, puis envoie `pg_dump | pg_restore --clean` dans le Cluster vivant vide et contrôle la chaîne canari ; `--db-source dump` restaure
le dump restic à la place (RPO 24 h, sans archive : le chemin quand l'archive de l'autre provider a disparu). `--scenario etcd` est l'étape 10 seule : restauration restic du dernier snapshot etcd, `talosctl bootstrap --recover-from` (avec `--recover-skip-hash-check` quand le
fichier n'a pas de suffixe sha256), et un contrôle que l'API et les nœuds sont revenus et que les agents Cilium ont été redémarrés (un agent bloqué en `Terminating` est supprimé de force une fois ; les autres étapes à la main sont dans « Restauration etcd sur place : les étapes à la main »). Les secrets sont lus dans des fichiers et passent par l'entrée standard ou en argument fichier, jamais dans argv ni dans la sortie.

### Avant une destruction planifiée : forcer la sortie du dernier segment de WAL

**Une sauvegarde de base finale terminée n'est pas un point de restauration utilisable tant que le segment de WAL qui la termine n'est pas archivé.** Dans un lab de preuve (Scaleway, 3 CP + 6 W) `backup-verify` a ÉCHOUÉ sur le store primaire environ 2 minutes après que le `Backup` du plugin des deux bases a dit `completed`, les écrivains étant arrêtés : `zitadel-db: backup 20261103T125412: end_wal 00000001000000000000000C is not archived (newest 11)`, et de même pour `grafana-db`. Les deux primaires étaient sur le segment 0C et le dernier archivé était 0B : les commits acquittés depuis le dernier changement de segment étaient dans 0C, que rien n'avait fait basculer. Détruire le cluster alors aurait arrêté l'archive à 0B et les aurait perdus. Sur le store réplica la nouvelle sauvegarde n'était pas encore là (`backup.info unreadable (NoSuchKey)`) : le job de copie retient `backup.info` tant que le segment qui termine la sauvegarde n'a pas été copié, règle que le `Backup` du plugin n'a pas.

Avant une destruction planifiée ou une migration, après la dernière sauvegarde et les écrivains arrêtés :

```bash
for c in zitadel-db grafana-db; do      # chaque Cluster CNPG depuis lequel vous restaurerez ; ceux de la plateforme ici
  p="$(kubectl -n foundation-databases get clusters.postgresql.cnpg.io "$c" -o jsonpath='{.status.currentPrimary}')"
  kubectl -n foundation-databases exec "$p" -c postgres -- psql -U postgres -X -At -c 'SELECT pg_switch_wal()'
  kubectl -n foundation-databases exec "$p" -c postgres -- psql -U postgres -X -At -c 'SELECT last_archived_wal, last_archived_time FROM pg_stat_archiver'
done
```

Relire `last_archived_wal` jusqu'à ce qu'il ait dépassé le segment que vous venez de faire basculer (2 s au lab), puis copier et vérifier de nouveau :

```bash
for j in cnpg-store-replicate backup-verify; do
  kubectl -n foundation-databases create job --from=cronjob/$j "final-$j" &&
    kubectl -n foundation-databases wait --for=condition=complete "job/final-$j" --timeout=900s
done
kubectl -n foundation-databases logs job/final-backup-verify --all-containers | grep -E '^(PASS|FAIL|SKIP) '
```

Ne détruire que lorsque `backup-verify` écrit `PASS` pour `cnpg/primary` ET `cnpg/replica` avec une plage de WAL qui atteint le WAL de fin de la nouvelle sauvegarde (`WAL 11..12 contiguous (12 segments)` pour les deux au lab). **Lire les lignes, pas le Job :** le Job de `backup-verify` s'est terminé `Complete` alors que son contrôle écrivait `FAIL`, par conception (un contrôle échoué est une ligne de journal et une métrique, `BackupVerificationFailed`, pas un Job échoué).

Coût au lab : 141 s pour les sauvegardes finales, puis 152 s pour ce tour. Jusqu'où va le risque : le `archive_timeout` de 5 minutes du cluster aurait dû archiver le segment 0C environ 5 minutes après le dernier changement, avant la destruction du lab (une déduction du réglage ; le lab a forcé le changement et n'a pas attendu), donc la fenêtre est une destruction dans les 5 minutes environ qui suivent le dernier changement, ou une restauration depuis le store réplica, qui traîne derrière le primaire de 15 minutes au plus plus la copie. Non changé en 0.4.1 : pas de tâche d'aide, et le `Backup` du plugin dit encore `completed` trop tôt ; la ligne `FAIL` dit ce qu'elle dit (`backup-verify` d'OpenAether-apps).

### La génération d'archive : ce qu'une reconstruction fait à l'archive CNPG (apps #153)

Un cluster reconstruit ne doit pas archiver dans le chemin du cluster mort : barman refuse une archive non vide pour un nouveau cluster (« Expected empty archive »), donc rien n'est archivé et aucune sauvegarde de base n'aboutit (lab 20). Le plugin Barman Cloud écrit sous
`<destinationPath>/<serverName>` et, par défaut, `serverName` est le nom du Cluster : le nouveau `zitadel-db` retrouvait les objets de l'ancien. Désormais un Cluster archive sous `serverName` = `<cluster>` + le **suffixe d'archive** : vide sur toute installation (génération 1,
le chemin historique : rien ne bouge pour un cluster existant ni pour une installation neuve), `-g2`, `-g3`… sur un cluster reconstruit depuis un store.

- **Où c'est consigné** : le ConfigMap `cnpg-archive-generation` dans `flux-system` (`CNPG_ARCHIVE_SUFFIX`, `CNPG_ARCHIVE_PREVIOUS_SUFFIX`, annotation `openaether.io/archive-generation`). Flux possède les Clusters et substitue la valeur (`postBuild.substituteFrom`, **optionnel** : pas de ConfigMap, pas de suffixe) dans le Cluster
  et dans la copie de `cluster-identity` que lisent le vérificateur et les jobs. Il n'est pas dans git et Flux ne l'élague pas ; `task dr-restore-plan` l'écrit. Personne ne modifie le Cluster à la main.
- **L'étape `generation`** (après `hold`) : liste `cnpg/<cluster>/` dans les deux stores (le store survivant doit répondre ; l'autre est compté s'il est lisible), prend la plus haute génération trouvée plus un, écrit le ConfigMap et le suffixe précédent. `--archive-generation N` impose le numéro (sans liste, sans `aws`).
  Un second passage garde la valeur consignée, car le nouveau cluster a pu écrire son propre chemin. L'étape `dbs` attend que Flux ait donné le nouveau nom aux Clusters **avant** de charger les données ; `--db-source pitr` récupère depuis le chemin de la génération PRÉCÉDENTE (celle du cluster mort) ; l'étape `verify` donne à
  chaque nouvelle archive une sauvegarde de base (`Backup dr-base-<cluster>`), force la sortie du segment (`pg_switch_wal`), exige `ContinuousArchiving` True, lance une fois `cnpg-store-replicate` pour que le store réplica contienne le nouveau chemin, puis seulement le test de restauration.
- **Ce qui suit le suffixe** : le vérificateur lit `cnpg/<cluster>/<cluster><suffixe>/` (la génération la plus récente seule) ; les tests de restauration CNPG (quotidien, point dans le temps) récupèrent depuis le serverName sous lequel le Cluster vivant archive maintenant ; `cnpg-store-replicate` copie tout le préfixe `cnpg/<cluster>/`, donc les deux
  générations. L'ancien chemin n'est plus jamais écrit.
- **RPO et chemins après une reconstruction** : un point dans le temps **antérieur** à la reconstruction se récupère depuis l'ANCIEN chemin (`--db-source pitr` le fait ; à la main, une entrée `externalClusters` avec `serverName: <cluster>` ou `<cluster>-g<N-1>`) ; un point postérieur, depuis le nouveau. Il n'y a pas d'historique continu à travers la
  reconstruction : entre le dernier WAL archivé du cluster mort et le premier du nouveau, n'existent que les données chargées par la chaîne. La nouvelle archive commence avec la sauvegarde de base de l'étape `verify` : tant qu'elle n'est pas terminée, la récupération du cluster reconstruit passe par l'ancien chemin et le dump. L'ancien chemin reste dans
  les deux stores jusqu'à ce que quelqu'un le supprime (hors de la rétention de 30 jours du nouveau serverName : à supprimer soi-même une fois la fenêtre de récupération passée ; le job de copie n'élague le réplica que pour les objets qui ont quitté le primaire).

**NON VÉRIFIÉ (tests hors ligne seulement : barreau mocked)** : que CNPG et le plugin acceptent un `serverName` modifié sur un Cluster existant (le pod peut demander un rollout ou l'annotation `cnpg.io/reloadedAt`) et ce que l'instance fait des tentatives d'archivage antérieures au changement ; que le `substituteFrom` optionnel de Flux se comporte comme la substitution
hors ligne (et que les deux briques, `cnpg` et `backup-databases-identity`, appliquent la même valeur en une réconciliation) ; `aws s3api list-objects-v2` avec délimiteur chez les trois providers ; que le `Backup` avec `method: plugin` écrit le nouveau chemin ; que `pg_switch_wal` suffit sur une base occupée ; la durée du travail ajouté à `verify`.

**Critères de réussite du prochain exercice** (tous requis ; aucun n'a été observé) : (1) après `generation`, `kubectl -n flux-system get cm cnpg-archive-generation` montre `-g2` (ou le numéro suivant) et le suffixe précédent ; (2) l'étape `dbs` passe son attente : les deux Clusters montrent `serverName` `<cluster>-g2`, `ContinuousArchiving` True quelques minutes après le chargement, pas de « Expected empty archive » dans le journal du sidecar ;
(3) dans le store primaire `cnpg/<cluster>/<cluster>-g2/base/<id>/backup.info` (status DONE) et `wals/…` existent pour les deux clusters, et les objets sous `cnpg/<cluster>/<cluster>/` sont inchangés (même nombre, même date la plus récente) dans les deux stores ; (4) `Backup` `dr-base-*` terminé, job `dr-replicate` Complete, le store réplica contient `-g2` ;
(5) l'étape `verify` passe avec `PASS` pour les quatre combinaisons (zitadel-db et grafana-db, primaire et réplica) et aucun `SKIP`, retards sous les budgets (1200 s primaire, 3000 s réplica), zitadel-db compris ; (6) le prochain passage de `backup-verify` rapporte `cnpg` primaire et réplica à 1 pour les deux clusters et `BackupVerificationFailed` ne se déclenche pas, le prochain `ScheduledBackup` quotidien aboutit sur `-g2`, les prochains tests de restauration quotidien et hebdomadaire sont PASS en lisant `-g2` ;
(7) un passage `--db-source pitr --pitr-time <avant la reconstruction>` récupère depuis l'ancien chemin ; (8) deux réconciliations de `cnpg` par Flux (suspend, resume) laissent le `serverName` et les pods en l'état ; (9) un `cluster-up` neuf sur des buckets neufs rend `serverName` = le nom du Cluster (pas de ConfigMap, rien n'a bougé).

### Les tests de restauration planifiés (0.4.0)

Depuis 0.4.0 la plateforme restaure ses propres sauvegardes sans personne (apps `backup/databases`, `cnpg` et le composant optionnel `storage-restore-test`) : `cnpg-recovery-restore-test` quotidien récupère zitadel-db et grafana-db depuis le store primaire ET le store réplica dans un Cluster jetable de
`backup-restore-test` et compare une table canari (un compteur et une chaîne de hachages écrits toutes les 5 minutes) avec la base vivante ; `cnpg-pitr-restore-test` hebdomadaire récupère à l'heure d'une ligne canari et doit finir exactement là ; `cnpg-dump-load-restore-test` quotidien charge les dumps restic des
deux dépôts dans un PostgreSQL privé ; `longhorn-restore-test` optionnel restaure chaque semaine un volume canari. Les résultats sont des métriques `oa_restore_test_*` avec `RestoreTestFailed`, `RestoreTestNoRecentPass` et les autres alertes de `vmrule-restore-test.yaml`. Un objet jetable est toujours supprimé, même
en cas d'échec, et un test de restauration ne peut jamais toucher un objet vivant (namespace, noms, RBAC et une politique Kyverno). Le snapshot raft d'OpenBao est contrôlé chaque jour jusqu'à ses sommes ; il n'est restauré dans un OpenBao que par cette chaîne.

**Points où la chaîne a une jonction non réglée** : (a) comment gagner l'étape 3 contre Flux sur un cluster monté avec Flux (suspendre `flux-system` dès que l'API répond, ou monter avec
`deploy_flux = false` et l'activer une fois le Secret posé) : pas essayé, c'est une étape de labo ; (b) si le réplica survivant contient le dépôt restic du **cluster mort** sous le préfixe
que le nouveau cluster attend (le préfixe du dépôt est le nom du cluster ; un nouveau nom de cluster demande l'ancien préfixe dans la commande) ; (c) la chaîne PITR est chez le provider
tombé en cas de perte de provider : seul le dump quotidien survit chez l'autre (RPO 24 h).

### Où la chaîne de reprise peut s'arrêter (lab 28B)

Le lab 28B (Scaleway, 2026-10-30, reconstruction NOMINALE sans panne : 3 CP + 7 W détruits, 3 CP + 6 W reconstruits, store réplica chez le même provider, OpenBao de DÉVELOPPEMENT, Flux sur une branche de lab) a chronométré la chaîne en une seule passe. **RTO mesuré : les données étaient revenues 43 min après le sinistre déclaré, et la chaîne était vérifiée de bout en bout 68 min 3 s après lui (cible 8 h, tenue d'un facteur 7).** Pour le dire franchement, **la chaîne n'est PAS sans surveillance** : elle s'est arrêtée deux fois avec un code non nul alors que les données étaient intactes (deux faux négatifs), et trois étapes ont été faites à la main. Un arrêt est bruyant (`✗ the chain stopped at '<étape>'; fix it and resume with --from-step <étape>`), jamais silencieux. **La 0.4.1 change le script pour les deux arrêts : `resume` ne réactive plus `observability` (Grafana), donc le chargement se fait dans un `grafana-db` vierge (infra #426) ; et les Jobs que la chaîne crée depuis les deux CronJobs perdent leur référence de propriétaire, donc la limite d'historique du CronJob ne peut plus les supprimer, et un Job malgré tout disparu fait échouer l'étape aussitôt au lieu de 900 s plus tard (infra #427). Rejoué sur un cluster dans deux labs de preuve de la 0.4.1 (ci-dessous) : aucun des deux arrêts n'est revenu (`dbs` s'est terminée en rc 0 et `verify` a trouvé son Job, les deux fois).** `observability` (Grafana, Loki, la pile de métriques) était réactivée par l'étape `resume` et convergeait pendant le chargement des bases ; elle l'est maintenant par l'étape `identity`, donc elle converge dans cette étape. **PIRE, mesuré : `identity` a duré 168 s (NOMINAL, 3 CP + 6 W) contre 10 s au passage du lab 28B, et la somme des étapes à périmètre égal est plus longue de 25 % (« Mesuré dans un second lab de preuve », ci-dessous).** Le tableau et les étapes à la main restent la sortie de secours si un arrêt se produit quand même.

**Ce qu'un lab de preuve a trouvé dans le code 0.4.1 ci-dessus** (Scaleway, 3 CP + 6 W, un OpenBao de développement, le store réplica chez le même provider, la reconstruction elle-même NOMINALE). Trois défauts et un piège. Les corrections ci-dessous ont été testées contre le double, puis rejouées sur un cluster dans un second lab de preuve de même forme, où chacune a tenu (« Mesuré dans un second lab de preuve », ci-dessous).

1. **La retenue de `observability` et `identity` ne tenait pas (infra #426).** `hold` suspendait 33 Kustomizations, `openaether-platform` parmi elles (il est hors de la fermeture d'OpenBao), et `resume` reprenait ensuite tout sauf `identity*` et `observability`, le parent compris. Le parent applique toutes les autres Kustomizations, dont les manifestes ne portent pas de `spec.suspend` : sa première réconciliation a donc remis les deux à zéro, et les pods de Grafana et le Job `init` de Zitadel ont été créés quand `cnpg` est devenu prêt, pendant que `dbs` chargeait encore. Un test en direct a confirmé le mécanisme (un enfant suspendu avec le patch de la chaîne était revenu à non défini en moins de 10 s après une réconciliation forcée du parent). Rien n'a été perdu (l'instance Zitadel d'origine était intacte et `dbs` s'est terminé OK) : c'était le hasard du calendrier, pas une garantie. Maintenant `hold` suspend le parent EN PREMIER et relit chaque Kustomization retenue comme suspendue (une qui a été remise à zéro est suspendue de nouveau ; après 3 essais l'étape s'arrête et la nomme), `resume` laisse le parent et le groupe tardif tranquilles, et `identity` reprend le groupe tardif, puis le parent EN DERNIER. `hold` dure au moins une pause (`OA_DR_POLL`, 10 s) de plus que les 5 s qu'elle durait. Sur un cluster l'étape a duré 16 s contre 5 s et 6 s (PIRE de 11 s, NOMINAL, 3 CP + 6 W) et a retenu 33 Kustomizations, le parent d'abord, chacune relue comme suspendue ; le parent, `identity` et `observability` sont restés suspendus pendant tout `dbs` et ont été libérés 1 s après sa fin, et le premier objet Zitadel a été créé 4 s plus tard. La relecture est une seule lecture propre après une pause de `OA_DR_POLL` : elle ne prouve pas qu'une réconciliation du parent déjà en cours au moment de sa suspension est terminée (la condition `Reconciling` du parent n'est pas lue). 2. **Le contrôle des ExternalSecrets de l'étape `identity` ne pouvait jamais passer sur une installation par défaut (une régression de la première version 0.4.1).** Il comptait `services-observability/grafana-oidc`, qui lit `grafana/oidc` (identifiant et secret du client OIDC de Grafana) : rien ne sème cette clé, un opérateur crée le client dans la console de Zitadel et met les identifiants dans OpenBao, et Grafana démarre sans eux. Dans le second lab de preuve l'étape a passé sur une installation par défaut en 168 s et a écrit que `grafana-oidc` n'est pas compté. Maintenant cet unique ExternalSecret, par espace de noms et nom, est écarté du compte tant qu'il n'est pas prêt et il est nommé dans la sortie ; les 18 autres restent comptés, les clés S3 de Loki et les URL d'Alertmanager comprises, comme la couverture de l'étape `resume` (tous les ExternalSecrets qui existent). `OA_DR_ES_OPTIONAL` (`espace/nom`, séparés par des virgules ou des espaces) remplace la liste ; vide, elle compte de nouveau tous les ExternalSecrets.

Les trois étapes à la main, avec les commandes exactes (namespace `foundation-databases` ; depuis la racine de ce dépôt) :

1. **Le jeton break-glass entre deux segments.** L'étape `openbao` demande `--bao-token-file`, un jeton root du cluster FRAIS, qui n'existe pas avant que l'étape `flux` l'ait construit. Lancer la chaîne en deux segments : `--only artifacts,cluster,seedkey,flux,hold,generation` (1 047 s au lab), fabriquer le jeton (`bao operator generate-root`, un quorum de porteurs de parts : apps `vault/README.md` ; avec l'amorçage de développement, une part en clair, environ 3 s), l'écrire dans un fichier lisible par vous seul, puis `--from-step openbao --bao-token-file <fichier>`.
2. **Le contrôle canari et le nettoyage des Clusters jetables après l'arrêt de `dbs`.** Le contrôle du script lui-même, depuis la racine du dépôt (il demande `python3` ; `$CANARY_SQL` et `$CANARY_PY` sont extraits du script, donc ne peuvent pas dériver) :

   ```bash
   eval "$(sed -n '/^CANARY_PY=/,/^CANARY_SQL=/p' scripts/ops/dr-restore-plan.sh)"
   for pair in zitadel-db:zitadel grafana-db:grafana; do
     c="${pair%%:*}"; db="${pair##*:}"
     p="$(kubectl -n foundation-databases get clusters.postgresql.cnpg.io "$c" -o jsonpath='{.status.currentPrimary}')"
     kubectl -n foundation-databases exec "$p" -c postgres -- psql -U postgres -d "$db" -X -At -F "$(printf '\t')" -c "$CANARY_SQL" | python3 -c "$CANARY_PY"
   done
   kubectl -n foundation-databases delete clusters.postgresql.cnpg.io zitadel-db-dr grafana-db-dr --ignore-not-found --wait=false
   ```

   Attendu : `canary chain intact, newest row <une heure juste avant le sinistre>` deux fois (une chaîne rompue affiche `canary chain broken at <compteurs>` et sort en 1 : c'est un vrai échec). Le lab a lancé exactement cela et obtenu `canary chain intact` deux fois, avec les lignes témoins (5 000 par base) et leurs sommes identiques à celles prises avant le sinistre.
3. **Le test de restauration du cluster reconstruit (`dr-check`) à la main**, après l'arrêt de `verify` :

   ```bash
   kubectl -n foundation-databases delete job dr-replicate dr-check --ignore-not-found
   kubectl -n foundation-databases create job --from=cronjob/cnpg-store-replicate dr-replicate
   kubectl -n foundation-databases patch job dr-replicate --type merge -p '{"metadata":{"ownerReferences":null}}'
   kubectl -n foundation-databases wait --for=condition=complete job/dr-replicate --timeout=900s
   kubectl -n foundation-databases create job --from=cronjob/cnpg-recovery-restore-test dr-check
   kubectl -n foundation-databases patch job dr-check --type merge -p '{"metadata":{"ownerReferences":null}}'
   kubectl -n foundation-databases wait --for=condition=complete job/dr-check --timeout=900s
   kubectl -n foundation-databases logs job/dr-check --all-containers | grep -E '^(PASS|SKIP|FAIL) '
   ```

   Réussi veut dire **quatre lignes `PASS`** (zitadel-db et grafana-db, chacune depuis le store primaire et le store réplica), aucun `SKIP`, aucun `FAIL` : un passage qui saute toutes les combinaisons finit aussi `Complete`, c'est pourquoi le script lit les lignes (lab 20). Le lab a obtenu quatre `PASS`, chaque récupération saine en 66, 66, 78 et 72 s. Les deux lignes `patch` (ce que fait le script depuis la 0.4.1) retirent la référence de propriétaire, donc le CronJob ne peut pas supprimer les Jobs ; sans elles `wait` répond `NotFound` pour `dr-replicate` dès que l'exécution planifiée suivante est terminée, ce qui veut dire que le Job s'est terminé, avec succès ou non : lister le store réplica avant de continuer. Les deux Jobs restent jusqu'à ce que vous les supprimiez ou que la prochaine exécution le fasse.

**Depuis la 0.4.1 l'étape `openbao` attend un état stable, pas un instant** (elle remplace le contrôle unique de la première version 0.4.1, point 3 ci-dessus ; elle supprime toujours `openbao-1` et `-2` une fois, comme avant). Après la restauration elle fait le tour des trois pods toutes les `OA_DR_POLL` (10 s) avec `bao status` et `bao read -format=json sys/leader` (sans jeton). Elle se termine après `OA_DR_STABLE_ROUNDS` (5) tours de suite où chaque pod est descellé, connaît un nœud actif et répond comme au tour d'avant ; un changement du nœud actif recommence le compte, et après `OA_DR_STABLE_TRIES` (60) tours la chaîne s'arrête avec l'état de chaque pod. Un pod scellé, ou sans nœud actif, pendant `OA_DR_STANDBY_TRIES` (18) tours de suite est redémarré une fois, `openbao-0` compris, UN pod par tour et seulement tant que les deux autres sont descellés et que l'un d'eux connaît un nœud actif : rien n'est redémarré quand un pod est arrêté (celui qu'on vient de redémarrer compris), ni quand aucun pod n'a de nœud actif (une élection ; la chaîne attend, puis s'arrête). Un pod encore mauvais après son redémarrage arrête la chaîne avec la commande exacte `kubectl delete pod`. `openbao-0` encore scellé après la restauration n'est pas redémarré par le script : la chaîne s'arrête avec la même commande. Un pod qui ne répond pas du tout revient au StatefulSet ; un pod dont `sys/leader` n'est pas lisible donne un avertissement. Les règles sont le commentaire au-dessus de `OPENBAO_PODS` dans `scripts/ops/dr-restore-plan.sh`. `OA_DR_NO_STANDBY_FIX=1` coupe tout cela. **Mesuré : 296 s (NOMINAL, 3 CP + 6 W, le second lab de preuve) contre 20 s et 9 s : PIRE exprès, le prix de la garantie ; la cible de l'étape est de 60 minutes.** Les 296 s s'additionnent à partir des constantes lues dans le code (un délai de grâce de 180 s, le redémarrage, cinq relevés espacés de 10 s) ; elles n'ont pas été chronométrées séparément, car les lignes du journal arrivent ensemble. **Prouvé une fois sur un cluster (une exécution) :** la chaîne a redémarré `openbao-0` elle-même (`without an active node: restarted once`), cinq relevés d'affilée ont ensuite trouvé les trois pods descellés avec le même nœud actif, et 23 sondages sur les 22 min 58 s suivantes n'ont trouvé aucun pod sans adresse de leader et une connexion Kubernetes-auth qui a marché sur les trois à chaque fois ; aucun pod n'a été supprimé à la main. Les 2 min 27 s qui suivent l'étape n'ont pas de preuve de connexion valide. **La cause n'est pas supprimée :** après la restauration raft `openbao-0`, où elle a tourné, reste sans leader, et la chaîne le contourne par le délai de grâce et un redémarrage. À la main : `kubectl -n foundation-vault exec openbao-N -- bao read sys/leader` sur chaque pod, et `kubectl -n foundation-vault delete pod openbao-N` pour celui dont `leader_address` est vide ou qui est scellé. **Ne pas utiliser `--only openbao` ni `--from-step openbao` pour revérifier un cluster restauré** : ils restaurent le snapshot de nouveau, et un pod a été vu scellé après une seconde restauration (la cause n'est pas établie) ; reprendre à `shares`. Et la **restauration etcd** sur place (`--scenario etcd`, hors de la chaîne de reconstruction et des 68 minutes) a rendu l'API en 3 minutes environ après la réinitialisation, mais la plateforme n'est pas revenue seule (un agent Cilium bloqué en `Terminating`, un nœud dont les pods sont restés injoignables jusqu'à son redémarrage, des contrôleurs à relancer) : environ 42 minutes jusqu'à un `cluster-verify` vert ; sa recette est la section suivante.

**La restauration raft d'OpenBao est prouvée avec l'amorçage de DÉVELOPPEMENT seulement.** `bao operator raft snapshot restore -force` a donné un leader à 3 membres en 7,4 s (lab 28B) et 8 s (lab 27 séance 3), et l'étape `openbao` a pris 9 s dans la chaîne (restauration restic depuis le store réplica comprise). Le jeton break-glass venait de l'unique part de récupération en clair de cet amorçage. Une restauration de type production (parts de récupération chiffrées aux clés PGP des porteurs, un quorum qui fabrique le jeton) demande les clés de récupération que détient le propriétaire et n'a **pas été jouée** : le RTO de 8 h ne dit rien du temps des personnes qu'elle demande.

### Après une reconstruction : `iam-admin` et `iam-admin-pat` ont disparu

Après la reconstruction du lab de preuve les Secrets `iam-admin` (la clé de l'utilisateur machine) et `iam-admin-pat` (son jeton) n'existaient pas dans `services-identity` : la lecture de `iam-admin-pat` répondait NotFound, et une lecture des Secrets de tout le cluster correspondant à `iam-admin` n'en trouvait aucun. La chaîne ne restitue ni l'un ni l'autre. La cause est une lecture, pas un test : l'installation de première instance de Zitadel ne tourne qu'une fois, à la création de l'instance, et la base restaurée contient déjà l'instance, donc le Job de setup ne crée aucun des deux Secrets. Que OpenBao les détienne n'a pas été lu. **Le chemin de retour que `zitadel-hardening.md` d'OpenAether-apps décrit pour un administrateur humain verrouillé (le déverrouiller avec le PAT), et tout script qui utilise le PAT, ne sont donc pas disponibles après une reconstruction.**

Ce qui existe à la place, dans la mesure de ce qui a été lu :

- **Les données d'identité.** La base `zitadel` restaurée contient l'instance du cluster mort et l'utilisateur créé avant le sinistre (une lecture SQL : ses huit événements, avec le contrôle du mot de passe et l'enrôlement TOTP). Un administrateur humain garde ce qu'il avait. Se reconnecter après une reconstruction n'a PAS été montré : le chemin du lab était scripté et demandait le PAT.
- **Une nouvelle clé machine, par un humain.** Un humain ayant le rôle propriétaire peut créer un utilisateur de service et une clé ou un jeton dans la console de Zitadel. Non essayé après une reconstruction.

### Restauration etcd sur place : les étapes à la main (lab 28B)

`--scenario etcd` (l'étape 10 seule) remplace l'etcd du MÊME cluster par son propre snapshot et perd tout ce qui a été écrit depuis ; le snapshot d'un autre cluster ne peut pas être restauré dans un cluster reconstruit (lab 20). Le lab 28B (Scaleway, 3 CP + 6 W, **INCIDENT** : la plateforme n'est pas revenue seule ; hors des 68 minutes de la chaîne de reconstruction) l'a chronométrée : la partie Talos a pris moins de 5 minutes, et **environ 42 minutes** ont été nécessaires pour un `cluster-verify` vert. Dans l'ordre :

1. **Réinitialiser les control planes, puis lancer le script.** Le lab a réinitialisé les trois (`talosctl reset --graceful=false --reboot --system-labels-to-wipe EPHEMERAL`, EPHEMERAL effacée), attendu l'API Talos, puis lancé `task dr-restore-plan PROVIDER=<p> -- --scenario etcd [--from replica] [--control-plane-ip <l'adresse propre du nœud>] --execute --confirm <cluster_name>` : `etcd-fetch` 2 s (depuis le store réplica), `etcd-recover` 3 s (`bootstrap --recover-from`, 104 Mo), et l'API et les 9 nœuds revenus environ 3 minutes après la réinitialisation ; le marqueur écrit avant le snapshot était là, celui écrit après avait disparu, trois membres etcd.
2. **Un agent Cilium bloqué en `Terminating`.** `etcd-check` redémarre les agents et l'opérateur Cilium (leurs watches datent d'avant la révision restaurée). Au lab, le déploiement a attendu ses 300 s sur l'agent d'un worker. Depuis la 0.4.1 le script supprime de force un pod d'agent `Terminating` après cette borne, une fois, et attend une seconde fois (les mêmes 300 s : l'étape n'est pas plus rapide, elle se passe de personne). **NON VÉRIFIÉ sur un cluster** (double hors ligne seulement). À la main : `kubectl -n kube-system get pods -l k8s-app=cilium -o wide`, puis `kubectl -n kube-system delete pod <pod-cilium> --grace-period=0 --force`. Le risque d'une suppression forcée est un second agent sur le nœud pendant que l'ancien est encore en train d'être tué ; le lab l'a fait à la main et aucune conséquence n'est notée.
3. **Un nœud dont les pods restent injoignables.** Le lab a vu les pods d'un worker injoignables depuis les autres nœuds une fois les agents revenus (les réplicas CNPG « could not connect to grafana-db-rw », l'opérateur CNPG « i/o timeout » sur le port de statut du primaire) jusqu'à ce que ce nœud soit **redémarré**. Pas scripté, volontairement : le script ne sait pas distinguer un datapath mort d'un datapath lent, et un redémarrage ne s'annule pas. Le lab a redémarré le nœud par un `talosctl reboot` propre (« graceful ») ; sa trace n'en dit pas plus : les options ne sont pas notées. Redémarrer le nœud (`talosctl -n <ip-du-nœud> reboot`), un nœud à la fois, un control plane seulement tant que les deux autres sont sains.
4. **Des contrôleurs en boucle de plantage.** Au lab, `source-controller`, les contrôleurs Cluster API et l'admission de Kyverno ont planté en boucle jusqu'à la suppression de leurs pods, et des pods `Error` périmés restaient. À la main : `kubectl get pods -A | grep -vE 'Running|Completed'`, puis `kubectl delete pod` sur ceux qui plantent en boucle (leurs Deployments les recréent) et sur les `Error` périmés.
5. **Vérifier.** `task cluster-verify` jusqu'au vert : au lab 27 réussis, 0 échec, 41 Kustomizations sur 41 prêtes, les deux Clusters CNPG de la plateforme à 3/3.

Les étapes 3 et 4 sont ce qu'aucun script ne fait encore. La recette et le changement Cilium ne sont pas exercés tels quels ; le prochain lab pourra rejouer le scénario etcd et, s'il le fait, cette section recevra ses chiffres.
