# Disaster recovery — one ordered chain, from nothing to a working platform

🇫🇷 [Version française](disaster-recovery.fr.md)

> Written to answer ANSSI rules on a documented recovery plan, time targets and a recovery test (audit id F-BKP-16). It links the
> existing pieces in the order that works, and since 0.4.0 `task dr-restore-plan` runs them in that order; **the chain as a whole has been run on clusters (a throwaway one in lab 20, Scaleway rebuilds in lab 28B and in two proof labs of 0.4.1, below), never unattended**: the rung is
> said for each step, and what a run needed by hand is listed below. The time targets are proposals, not
> measurements. It claims no compliance with any ANSSI document.

Read `backup-policy.md` first for what is copied, and `incident-response.md` if the reason for the recovery is an attack (choose a
restore point older than T0, close the door first, rotate after restoring).

## 1. Which disaster

| Situation | Path |
|---|---|
| One node lost or misbehaving | `rolling-replace` (`upgrade.md`, "Replacing a node"): not this page |
| The cluster is gone, the provider and the buckets are fine | sections 2 and 3, on the same provider |
| The provider is gone (account, region, the primary store) | sections 2 and 3, starting from the replica on the other provider: `cluster/README.md`, "Cross-provider failover" |
| The state lost its Talos secrets but the nodes live | `cluster/README.md`, "Lost the Talos secrets": not a rebuild |
| Only OpenBao lost its data | section 3 from step 5 |
| An attack | `incident-response.md` first |

## 2. Prerequisites: what must already be outside the cluster

If one of these is missing, the corresponding step cannot be done; the recovery objective then changes to "rebuild without that data".

| Needed | Held by | Lost means |
|---|---|---|
| K5 (and K6 if set) | the operator's vault, two places ideally | the state, artifacts and snapshots are unreadable: **no recovery of the Talos PKI**; rebuild with a new PKI |
| Object-store keys of the **surviving** store (`<PU>_BACKUP_AWS_*` or the primary's) and provider credentials | `.env.sh`, the vault | create new ones at the provider; they are not the keys of any secret |
| The cluster's tfvars (`envs/<role>-<provider>.tfvars`, gitignored) | the operator's machine | rebuild it from the `.example` with the cluster name, environment, `bucket_suffix`, replica endpoint and region (`cluster/README.md`) |
| The OpenBao seal key (escrow, two custodians) | `docs/admin-access.md` section 1; apps Day 0 | **every OpenBao secret and every raft snapshot is lost** |
| The OpenBao recovery shares (PGP-encrypted) and the holders' private keys | the operators | no break-glass: the restore needs a root token |
| The restic password (escrow) | the vault | the application backups are unreadable |
| This repository at the tag that built the cluster, and OpenAether-apps at the `git_ref` it pinned | GitHub, and the operator's clone | build from the tag you can pull; nothing here is vendored |

## 3. The chain

Do the steps in this order. A step that fails stops the chain: do not skip ahead to "get something up".

| # | Step | How | Why this position | Rung and target (proposed) |
|---|---|---|---|---|
| 1 | Access to the old cluster's identity | `task restore-artifacts PROVIDER=<p> [FROM=replica]` for the talosconfig and kubeconfig; `task restore-state` for the state if the provider changed | Everything after needs the state (it holds the Talos PKI) and, for a cross-provider rebuild, the old kubeconfig to check against | Both measured on real stores (`backup-policy.md`). 30 min |
| 2 | Cluster | `task cluster-up PROVIDER=<p> [ROLE=…]` with the tfvars; the state, then the nodes, then Flux if `deploy_flux = true` | Nothing else exists without nodes | Measured `cluster-up`: 545 s to 1661 s on the three clouds, the longer ones including an image build (`status.md`). 1 to 2 h |

Restore from the restic dump (`pg_restore … --clean --if-exists`) or by point in time into a new Cluster (apps `backup/README.md`) | The masterkey in OpenBao (step 5) must already be in place: a database restored under a different masterkey is unusable | `dr-restore-plan` step `dbs` (PITR through a scratch Cluster, or the dump); the recovery itself ran by hand and is now tested daily; **the load into a live Cluster has not been run on a cluster**. 1 h |

**Proposed time target for the whole chain: 8 hours of work, one working day (RTO), data as of the last good backup (RPO below).** The sum of the
step targets above is about 6.5 hours. Lab 20 timed the chain on a throwaway cluster: 31 minutes of steps (below); the proposal stays until a drill of a production shape.

### One command

`task dr-restore-plan` is the table above as a command (`scripts/ops/dr-restore-plan.sh`; it adds no mechanism, every step calls a command that exists). It is a **dry-run by default**: it prints each step with the commands for THIS
cluster (its buckets, repositories and store), the inputs each step still needs and which are missing, and runs nothing. Run it, with `--strict`, before the day you need it. `--execute --confirm <cluster_name>` runs the
chain, a check after each step, and stops at the first failure with the step to resume from; it writes a timing report (a TSV, seconds and target per step, the wall clock against the 8 h) to fill the table of section 5.

```bash
task dr-restore-plan PROVIDER=scaleway -- --from replica                         # dry-run: ordered steps, this cluster's commands, missing inputs
task dr-restore-plan PROVIDER=scaleway -- --from replica --strict --seal-key-file F --restic-password-file F \
  --bao-token-file F --recovery-shares-dir D                                     # readiness: exits 1 if an input is missing
task dr-restore-plan PROVIDER=scaleway -- --from replica --seal-key-file F --restic-password-file F --bao-token-file F \
  --recovery-shares-dir D --execute --confirm <cluster_name>                     # the chain; --from-step <id> resumes, --only <id,id> runs a subset
```

Steps (rebuild scenario): `artifacts` (1), `cluster` (2, with `deploy_flux = false`), `seedkey` (3), `flux` (4: `deploy_flux = true`, a second `task cluster-up`; the previous tfvars is kept as `.dr-bak`), `hold` (the Kustomizations outside OpenBao's dependency
closure are suspended, their parent `openaether-platform` first, and every one is read back as suspended), `generation` (the new CNPG archive generation, below), `openbao` (5), `shares` (6), `resume` (7: everything held except `identity*`, `observability`, which carries Grafana, and the parent `openaether-platform`), `dbs` (8), `identity` (9: identity and observability, then the parent `openaether-platform` last, which re-applies the rest; it waits for the DAG and for every ExternalSecret to be Ready, Grafana's and Loki's included, except `services-observability/grafana-oidc`, which is named in the output when it is NotReady; `OA_DR_ES_OPTIONAL` replaces that list, empty counts every ExternalSecret), `verify` (11: `cluster-verify`, a base backup of each new archive and its copy to the replica store, then a restore test run on the rebuilt cluster). `--db-source pitr` (default) recovers each
CNPG database from the ObjectStore of the chosen store (optionally `--pitr-time`) into a scratch Cluster `<name>-dr`, then streams `pg_dump | pg_restore --clean` into the empty live Cluster and checks the canary chain; `--db-source dump` restores the
restic dump instead (RPO 24 h, no archive needed: the path when the other provider's archive is gone). `--scenario etcd` is step 10 alone: restic restore of the newest etcd snapshot, `talosctl bootstrap --recover-from` (with `--recover-skip-hash-check` when the
file has no sha256 trailer), and a check that the API and the nodes are back and that the Cilium agents were restarted (an agent stuck `Terminating` is force-deleted once; the other hand steps are in "In-place etcd restore: the hand steps"). Secrets are read from files and travel on stdin or as file arguments, never in argv or in the output.

### Before a planned destruction: force the last WAL segment out

**A completed final base backup is not a usable restore point until the WAL segment that ends it is archived.** In a proof lab (Scaleway, 3 CP + 6 W) `backup-verify` FAILED on the primary store 86 s after the plugin `Backup` of both databases said `completed`, with the writers stopped: for both databases the end WAL of the new backup, segment 0C, was not archived yet. Both primaries were on segment 0C and the last archived one was 0B: the commits acknowledged since the last switch sat in 0C, which nothing had switched out. Destroying the cluster then would have ended the archive at 0B and lost them. On the replica store the new backup was not there yet (`backup.info unreadable (NoSuchKey)`): the copy job keeps `backup.info` back until the segment that ends the backup has been copied, a rule the plugin `Backup` does not have. The lab ran the 0.4.0 wording of the `backup-verify` message, which gives the newest archived segment as a decimal number; since OpenAether-apps 0.4.1 it names both segments in hex, says that the Backup is not a usable restore point yet and what to do. **The backup README of OpenAether-apps** (`apps/base/backup/README.md`, "A completed Backup is not a restore point yet") **is the authoritative text** for the rule, its limits and the order; this page keeps the commands.

Before a planned destroy or a migration, after the last backup and with the writers stopped, switch the segment on each primary and wait until it is archived. The block names the segment it switches out (`pg_switch_wal()` itself returns only an LSN) and waits up to 60 s (2 to 4 s in the lab):

```bash
ns=foundation-databases
for c in zitadel-db grafana-db; do      # every CNPG Cluster you will restore from; the platform ones here
  p="$(kubectl -n $ns get clusters.postgresql.cnpg.io "$c" -o jsonpath='{.status.currentPrimary}')"
  q() { kubectl -n $ns exec "$p" -c postgres -- psql -U postgres -X -At -c "$1"; }
  seg="$(q 'SELECT pg_walfile_name(pg_current_wal_lsn())')"      # the segment about to be switched out
  q 'SELECT pg_switch_wal()' >/dev/null
  for _ in $(seq 30); do                                          # up to 60 s
    [ "$(q "SELECT last_archived_wal COLLATE \"C\" >= '$seg' FROM pg_stat_archiver")" = t ] && break
    sleep 2
  done
  echo "$c: switched out $seg, last archived $(q 'SELECT last_archived_wal FROM pg_stat_archiver')"
done
```

If a segment is still not archived after 60 s, do not go on: the verify below will say so. Then copy and verify again. The block deletes the Jobs of an earlier round first, so that a retry neither stops on `AlreadyExists` nor reads the `PASS` or `FAIL` of the old run, and takes the CronJob's owner reference off the new Jobs (the patch the chain makes, infra #427), so that its history limit cannot prune one before you read it:

```bash
ns=foundation-databases
kubectl -n $ns delete job final-cnpg-store-replicate final-backup-verify --ignore-not-found   # a retry must not read the old run
for j in cnpg-store-replicate backup-verify; do
  kubectl -n $ns create job --from=cronjob/$j "final-$j" &&
    kubectl -n $ns patch job "final-$j" --type merge -p '{"metadata":{"ownerReferences":null}}' &&
    kubectl -n $ns wait --for=condition=complete "job/final-$j" --timeout=900s || break
done
kubectl -n $ns logs job/final-backup-verify --all-containers | grep -E '^(PASS|FAIL|SKIP) '
```

Destroy only when `backup-verify` prints `PASS` for `cnpg/primary` AND `cnpg/replica` with the WAL range reaching the end WAL of the new backup (`WAL 11..12 contiguous (12 segments)` for both in the lab). **Read the lines, not the Job:** the Job of `backup-verify` ended `Complete` while its check printed `FAIL`, by design (a failed check is a log line and a metric, `BackupVerificationFailed`, not a failed Job).

Cost in the lab: 141 s for the final backups, then 152 s for this round. How far the risk reaches: the cluster's own `archive_timeout` of 5 minutes should have archived segment 0C about 5 minutes after the last switch, before the destroy of the lab (an inference from the setting; the lab forced the switch and did not wait), so the window is a destroy within about 5 minutes of the last switch, or a restore from the replica store, which trails the primary by up to 15 minutes plus the copy. Not changed in this repository for 0.4.1: there is no helper task and the plugin `Backup` still reports `completed` early; only the `backup-verify` message of OpenAether-apps is clearer. The two blocks are what the lab did by hand, made safe to repeat: as written they were checked against a stub `kubectl` (the calls and the quoting), never run on a cluster.

### The archive generation: what a rebuild does to the CNPG archive (apps #153)

A rebuilt cluster must not archive into the dead cluster's path: barman refuses a non-empty archive for a new cluster ("Expected empty archive"), so nothing is archived and no base backup completes (lab 20). The Barman Cloud plugin writes under
`<destinationPath>/<serverName>` and, by default, `serverName` is the Cluster name, so the new `zitadel-db` met the old one's objects. Since the fix a Cluster archives under `serverName` = `<cluster>` + the **archive suffix**: empty on every install (generation 1, the historical
path, nothing moves for an existing cluster or a fresh install), `-g2`, `-g3`… on a cluster rebuilt from a store.

- **Where it is recorded**: the ConfigMap `cnpg-archive-generation` in `flux-system` (`CNPG_ARCHIVE_SUFFIX`, `CNPG_ARCHIVE_PREVIOUS_SUFFIX`, annotation `openaether.io/archive-generation`). Flux owns the Clusters and substitutes the value (`postBuild.substituteFrom`, **optional**: no ConfigMap means no
  suffix) into the Cluster, and into the copy of `cluster-identity` the verifier and the jobs read. It is not in git and not pruned by Flux; `task dr-restore-plan` writes it. Nobody edits the Cluster by hand.
- **The `generation` step** (after `hold`, before the cluster's databases exist from a store): lists `cnpg/<cluster>/` in both stores (the surviving store must answer; the other is counted if it can be read), takes the highest generation found plus one, writes the ConfigMap, records the previous suffix. `--archive-generation N`
  forces the number (no listing, needs no `aws`). A re-run keeps the recorded value, because the new cluster may already have written its own path. Step `dbs` waits until Flux has given the Clusters the new name **before** the data is loaded; `--db-source pitr` recovers from the PREVIOUS
  generation's path (the dead cluster's); step `verify` gives each new archive a base backup (`Backup dr-base-<cluster>`), forces the segment out (`pg_switch_wal`), requires `ContinuousArchiving` True, runs `cnpg-store-replicate` once so the replica store holds the new path, and only then runs the restore test.
- **What follows the suffix**: the verifier reads `cnpg/<cluster>/<cluster><suffix>/` (the newest generation only); the CNPG restore tests (daily, point in time) recover from the serverName the live Cluster archives under now; `cnpg-store-replicate` copies the whole `cnpg/<cluster>/` prefix, so both generations are copied. The older path is never written again.
- **RPO and paths after a rebuild**: a point in time **before** the rebuild is recovered from the OLD path (`--db-source pitr` does it; by hand, an `externalClusters` entry with `serverName: <cluster>` or `<cluster>-g<N-1>`); a point in time after it, from the new path. There is no continuous history across the rebuild: between the last archived WAL of the dead
  cluster and the first of the new one only the data the chain loaded exists. The new archive starts with the base backup of the `verify` step, so until it completes a recovery of the rebuilt cluster uses the old path plus the dump. The old path stays in both stores until someone deletes it (it is outside the 30-day retention of the new
  server name: remove it yourself once the recovery window has passed; the copy job prunes the replica only for objects that left the primary).

**UNVERIFIED as written at the mocked rung (the rebuilds of the 0.4.1 labs ran the step and a Backup on the new path, and isolated none of these points)**: that CNPG and the plugin accept a changed `serverName` on a Cluster that already exists (the pod may need a rollout or the annotation `cnpg.io/reloadedAt`, docs of apps `traps.md`) and what the instance does with the archive attempts made before the change; that Flux's optional `substituteFrom` behaves as in
the offline substitution (and the two bricks, `cnpg` and `backup-databases-identity`, apply the same value within one reconcile); `aws s3api list-objects-v2` with a delimiter on the three providers; that the plugin's `Backup` with `method: plugin` writes the new path; that `pg_switch_wal` is enough on a busy database; the timing of the added `verify` work.

### The scheduled restore tests (0.4.0)

Since 0.4.0 the platform restores its own backups without a person (apps `backup/databases`, `cnpg` and the opt-in `storage-restore-test`): daily `cnpg-recovery-restore-test` recovers zitadel-db and grafana-db from the primary AND the replica store into a scratch Cluster in
`backup-restore-test` and compares a canary table (a counter and a hash chain written every 5 minutes) with the live database; weekly `cnpg-pitr-restore-test` recovers to the time of one canary row and must end exactly there; daily `cnpg-dump-load-restore-test` loads the restic dumps of
both repositories into a private PostgreSQL; the opt-in `longhorn-restore-test` restores a canary volume weekly. Results are `oa_restore_test_*` metrics with `RestoreTestFailed`, `RestoreTestNoRecentPass` and the other alerts of `vmrule-restore-test.yaml`. A scratch object is always removed, even
on failure, and a restore test can never touch a live object (namespace, names, RBAC and a Kyverno policy). The OpenBao raft snapshot is checked daily as far as its sums; it is restored into an OpenBao only by this chain.

**Points where the chain had an unsettled join** (lab 20): (a) step 3 against Flux: building with `deploy_flux = false`, creating the seal key Secret, then switching Flux on works; `hold` suspended 34 Kustomizations 6 s after the init Job completed and nothing consumed the throw-away values (the fresh bootstrap's generated Secrets were replaced by the restore); (b) the restic prefix of the surviving repositories is the cluster id `<cluster_name>-<environment>-<provider>` (not the bare name), and a new cluster name needs that prefix in the command; (c) the PITR chain is on the provider that failed in a provider loss: only the daily dump survives on the other one (RPO 24 h). Also learned: a cluster brought up after its state was destroyed has a new PKI, so the chain takes the new kubeconfig and talosconfig after each `cluster-up`; unattended, `OA_DR_TASK="task KEY=<ssh key> APPROVE=auto"` lets the chain's `cluster-up` run without a terminal; the databases are restored as the owner of the database (`--role`), not as postgres.

**Since 0.4.1 the `openbao` step waits for a stable state, not for a moment** (it replaces the one-shot check of the first 0.4.1 version, item 3 above; it still deletes `openbao-1` and `-2` once, as before). After the restore it surveys the three pods every `OA_DR_POLL` (10 s) with `bao status` and `bao read -format=json sys/leader` (no token). It ends after `OA_DR_STABLE_ROUNDS` (5) surveys in a row in which every pod is unsealed, names an active node and gives the same answer as the survey before; a move of the active node starts the count again, and after `OA_DR_STABLE_TRIES` (60) surveys the chain stops with the state of each pod. A pod sealed, or without an active node, for `OA_DR_STANDBY_TRIES` (18) surveys in a row is restarted once, `openbao-0` included, ONE pod per survey and only while the other two are unsealed and one of them names an active node: nothing is restarted while a pod is down (the one just restarted included), and none while no pod has an active node (an election; the chain waits, then stops). A pod still bad after its restart stops the chain with the exact `kubectl delete pod`. `openbao-0` still sealed after the restore is not restarted by the script: the chain stops with the same command. A pod that does not answer at all is the StatefulSet's to bring back; one whose `sys/leader` cannot be read is a warning. The rules are the comment above `OPENBAO_PODS` in `scripts/ops/dr-restore-plan.sh`. `OA_DR_NO_STANDBY_FIX=1` switches all of it off. **Measured: 296 s (NOMINAL, 3 CP + 6 W, the second proof lab) against 20 s and 9 s: WORSE on purpose, the price of the guarantee; the target of the step is 60 minutes.** The 296 s add up from the constants read in the code (a 180 s grace, the restart, five surveys 10 s apart); they were not timed apart, because the lines of the log arrive together. **Proven once on a cluster (one run):** the chain restarted `openbao-0` itself (`without an active node: restarted once`), five surveys in a row then found all three pods unsealed with the same active node, and 23 polls over the next 22 min 58 s found no pod without a leader address and a Kubernetes-auth login that worked on all three each time; no pod was deleted by hand. The first 2 min 27 s after the step have no valid login proof. **The cause is not removed:** after the raft restore `openbao-0`, where it ran, is left without a leader, and the chain works around it with the grace and a restart. By hand: `kubectl -n foundation-vault exec openbao-N -- bao read sys/leader` on each pod, and `kubectl -n foundation-vault delete pod openbao-N` for one whose `leader_address` is empty or that is sealed. **Do not use `--only openbao` or `--from-step openbao` to re-check a restored cluster**: they restore the snapshot again, and a pod was seen sealed after a second restore (the cause is not established); resume at `shares`. ### After a rebuild: `iam-admin` and `iam-admin-pat` are gone

After the rebuild of the proof lab the Secrets `iam-admin` (the machine user's key) and `iam-admin-pat` (its token) did not exist in `services-identity`: a read of `iam-admin-pat` answered NotFound, and a cluster-wide read of Secrets matching `iam-admin` found none. Lab 28B (Scaleway, 3 CP + 6 W, **INCIDENT**: the platform did not come back by itself; not part of the 68 minutes of the rebuild chain) timed it: the Talos part took under 5 minutes, and **about 42 minutes** went to a green `cluster-verify`. In order:

1. **Reset the control planes, then run the script.** The lab reset all three (`talosctl reset --graceful=false --reboot --system-labels-to-wipe EPHEMERAL`, EPHEMERAL wiped), waited for the Talos API, then ran `task dr-restore-plan PROVIDER=<p> -- --scenario etcd [--from replica] [--control-plane-ip <the node's own address>] --execute --confirm <cluster_name>`: `etcd-fetch` 2 s (from the replica store), `etcd-recover` 3 s (`bootstrap --recover-from`, 104 MB), and the API and 9 nodes back about 3 minutes after the reset; the marker written before the snapshot was there, the one written after it gone, three etcd members.
2. **A Cilium agent stuck `Terminating`.** `etcd-check` restarts the Cilium agents and operator (their watches predate the restored revision). In the lab the rollout waited its 300 s on one worker's agent. Since 0.4.1 the script force-deletes an agent pod that is `Terminating` after that bound, once, and waits once more (the same 300 s: the step is no faster, it needs no person). **UNVERIFIED on a cluster** (offline double only: the etcd scenario ran once more in a proof lab and no agent was stuck). By hand: `kubectl -n kube-system get pods -l k8s-app=cilium -o wide`, then `kubectl -n kube-system delete pod <cilium-pod> --grace-period=0 --force`. The risk of a force-delete is a second agent on the node while the old one is still being killed; the lab did it by hand and no consequence is recorded.
3. **A node whose pods stay unreachable.** The lab saw pods of one worker unreachable from the other nodes after the agents were back (the CNPG replicas "could not connect to grafana-db-rw", the CNPG operator "i/o timeout" on the primary's status port) until that node was **rebooted**. Not scripted, on purpose: the script cannot tell a dead datapath from a slow one, and a reboot cannot be undone. The lab rebooted the node with a graceful `talosctl reboot` (its record says no more: the flags are not recorded). Reboot the node (`talosctl -n <node-ip> reboot`), one node at a time, a control plane only while the other two are healthy.
4. **Controllers that crash-loop.** The lab's `source-controller`, the Cluster API controllers and Kyverno's admission controller crash-looped until their pods were deleted, and stale `Error` pods were left. By hand: `kubectl get pods -A | grep -vE 'Running|Completed'`, then `kubectl delete pod` on the ones that crash-loop (their Deployments recreate them) and on the stale `Error` ones.
5. **Verify.** `task cluster-verify` until green: in the lab 27 passed, 0 failed, 41 of 41 Kustomizations Ready, both platform CNPG Clusters 3/3.

Steps 3 and 4 are the part no script does yet. **Second run (a proof lab on Scaleway, 3 CP + 6 W, on the rebuilt cluster, INCIDENT-class by design):** the chain took 165 s (`artifacts` 3, `etcd-fetch` 3, `etcd-recover` 2, `etcd-check` 157); the API and the 9 nodes were back 234 s after the reset of the three control planes, `cluster-verify` was green at 362 s and everything healthy at 429 s (7 min 9 s, against about 42 minutes in lab 28B); the marker written before the snapshot was kept and the one written after it gone. **Only the easy half of the incident occurred:** step 4 was needed (17 pods crash-looping on stale informers 4 minutes after the reset, deleted once and recreated healthy within 50 s, plus one pod left bound to a node that did not know it), but no Cilium agent was stuck `Terminating` and no node had a dead datapath, so the force-delete of step 2 and the reboot of step 3 were NOT exercised.

## 4. Rebuild with data loss: when a prerequisite is missing

| Missing | What you can still do |
|---|---|
| The seal key | A new OpenBao, re-seeded: `seed-openbao.sh`, new Zitadel masterkey (the identity layer starts empty), new database passwords (databases restored from dumps cannot be used with them; restore the dump first, then align the role passwords), new restic password and **new repositories**; the old backups of OpenBao are unreadable |
| K5 and K6 | A new PKI: a new cluster from scratch; the old nodes cannot be administered; only the application backups (restic) remain |
| The restic password | The application backups are lost; new repositories |
| All recovery shares | No break-glass; restore needs a root token: a new OpenBao and the loss of its content |
| The surviving store | Rebuild from the Git repositories, and nothing else |
