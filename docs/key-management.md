# Key management — every key, how long it lives, what its loss or leak costs, how to replace it

🇫🇷 [Version française](key-management.fr.md)

> Written to answer the ANSSI rules on key impact, crypto-period, end of use, erasure and recovery
> (audit ids DP-06, DP-07, TLS-20, and the residual-risk entries of TLS-12 and TLS-19). It is a
> **document, not a control**: nothing here is enforced by code unless it says so, and **no procedure
> below was run on a cluster** unless it says so. It claims no compliance with any ANSSI document.
> Periods marked "proposed" are the maintainer's to confirm: the rules ask for a stated period, not for
> this one.

This page covers the keys of the platform underneath (Talos, the state, the buckets, the bastion) and lists
the keys of the application layer in one line each. The application layer's own inventory, with the same
columns and the replacement commands for OpenBao, restic, Zitadel and Longhorn, is
`OpenAether-apps/docs/key-inventory.md` (it ships with the apps side of the same ANSSI work; apps 0.2.0 does not have it).

## 1. Inventory: what each key is

"Where" names the place that must be protected. "Rung" is how the claim was established: **read** = from the
code in this repository, **upstream** = from the tool's documented default, not measured on this platform.

| # | Key | Purpose | Generated by, and where it lives | Algorithm | Crypto-period |
|---|---|---|---|---|---|
| K1 | Talos machine secrets (the PKI: Talos API CA, Kubernetes CA, etcd CA, aggregator CA, service-account key, bootstrap token) | Trust root of the nodes and the Kubernetes API | `talos_machine_secrets` (`modules/talos/main.tf`, `prevent_destroy`): tfstate (client-encrypted), every node's machine config, the state replica and its generations | chosen by the Talos library (upstream, not read) | CAs: 10 years from creation (upstream default, not measured); no renewal is scheduled |
| K2 | Admin `talosconfig` and `kubeconfig` | Operator access (`os:admin`, `system:masters`) | Issued from K1 by the Talos provider; `./talosconfig`, `./kubeconfig`, and gpg-encrypted copies in both artifact buckets | X.509 client certificates | talosconfig: about 1 year (`talosconfig-new.sh` header: "valid one year"); kubeconfig: the lifetime `talosctl kubeconfig` gives its client certificate (upstream default, not measured here); the `os:reader` file from `task talosconfig-new` defaults to 8 h |
| K3 | etcd Secrets-encryption key | Encrypts Kubernetes Secrets at rest in etcd | `random_bytes.etcd_encryption_secret`, 32 bytes: tfstate, control-plane machine configs | secretbox (XSalsa20-Poly1305); deviation recorded in `upgrade.md` | none; **not rotatable in place** (section 3) |

## 2. Inventory: impact, replacement, revocation, erasure

"Lost" is the key disappearing with no copy; "leaked" is an attacker holding it. **Impact is stated for the
system, not for the key**: the question each rule asks is what stops working, or what is exposed, and for how long.

| # | If lost | If leaked | Replacement | Revocation | Erasure and archive |
|---|---|---|---|---|---|
| K1 | The cluster stays up (the nodes hold their copies) but nothing new can authenticate: the replica generations are the way back (`cluster/README.md`, "Lost the Talos secrets"); with no copy anywhere, the decision is to rebuild | Full control of the Talos API and the Kubernetes API, for as long as the CA is trusted (10 years by default) | section 3, "Talos PKI"; the tested path is a **new cluster**; `talosctl rotate-ca` is the upstream in-place route, not run here | Only by replacing the CA: there is no revocation list for these certificates | Old state generations hold the PKI: delete them after a rotation (section 4) |
| K2 | Fetch again: `task kubeconfig`, `task restore-artifacts` | `system:masters` until the certificate expires: Kubernetes cannot revoke a client certificate (`admin-access.md`) | Issue a new one; the old stays valid until it expires | CA rotation only (K1) | The encrypted copies in both buckets age out with their objects; an old one opens with the old passphrase |
| K3 | Secrets in an etcd snapshot become unreadable; the live cluster is unaffected (the apiserver holds the key) | With a snapshot or an etcd disk: every Secret in clear. The cluster-side leak surface is the state, the machine configs and the snapshots | Rebuild (section 3) | Not revocable | Delete old snapshots and state generations |
| K4 | A node that reboots cannot unlock its disks; rebuild the node (`rolling-replace`) | With a stolen disk: its contents. Without the disk: nothing | Rebuild the nodes under a new value (section 3) | Not revocable | Same as K3 |
| K5 | The state and everything under K5 is lost: "no second key and no reset" (`first-cluster.md`). The replica holds the same ciphertext | Anyone who also reads a bucket object opens the state, hence K1, K3, K4 and every output | Section 3, "State passphrase" | Rotating the passphrase does not erase what the old one opens: old objects and generations must be deleted (section 4) | Archive: the old passphrase must be destroyed only after the last object under it is gone |
| K6 | Snapshots and artifacts written under it are unreadable (the state is unaffected) | Opens the artifacts and snapshots, not the state | Set a new value; the next apply re-uploads the artifacts; take a new snapshot | As K5 | As K5 |
| K7 | Backups and state stop being writable; the data is untouched | Read, overwrite or delete the state, the artifacts and the snapshots (all client-encrypted, so no read of the content, but the deletion is real: **no object lock is configured**) | Create a new key at the provider, update `.env.sh`, run a command that touches the bucket, then revoke the old key | At the provider | n/a |
| K8 | No infrastructure change possible | Destroy or create resources under the account | New key, then revoke | At the provider | n/a |
| K9 | The break-glass SSH access is lost; the provider console and a replacement bastion are the way back | Access to the admin path (the allowlist `admin_ip` and the node mTLS are still in front of the nodes) | Add the new key, replace the bastion (`admin-access.md`, offboarding) | `revoked_keys` (with the baseline on) or a CA that stops signing | Remove the key from the tfvars AND replace the bastion: `user_data` is read at first boot only |
| K10 | A recovery share cannot be decrypted by its holder: below quorum, no break-glass | One share alone is useless (PGP-encrypted); the quorum of holders' private keys together is root | `bao operator rekey` of the recovery keys (apps inventory) | A share cannot be revoked, only superseded | n/a |
| K11 to K13 | See `OpenAether-apps/docs/key-inventory.md` (columns "If lost", "If leaked", "Archive / erasure") | idem | idem | idem | idem |

Two facts the table rests on, because they decide the severity of K5: the tfstate holds K1, K3 and K4 (client-encrypted,
and replicated to a second provider's bucket together with up to five dated generations), so **K5 is the key to the keys**.
The split of K6 from K5 only separates the artifacts and snapshots if the two are kept in different places.

## 3. Replacement procedures

All of these are **written, not run**. Where a command comes from an upstream document it is said, and the
version of the client you hold (`talosctl` is installed at the cluster's own `talos_version`, `scripts/internal/install-talosctl.sh`) decides the flags: read `--help` first.

**Order of a rotation after an incident**: contain (`incident-response.md`, sections 3 to 6), then replace in the order of
that page's table (section 7), then erase (section 4 below). The target after a compromise is about one working day (ANSSI PG-078 R26);
no part of it has been timed.

### Talos PKI (K1) and admin credentials (K2)

- **The tested path is a new cluster.** `cluster/README.md` records the decision: a new PKI is a new cluster. Build the
  replacement beside or after the old one, restore OpenBao into it (`disaster-recovery.md`), re-seed what is outside OpenBao
  (`seed-openbao.sh`), cut over, then destroy the old one and erase its state generations.
- **In place, upstream's route**: `talosctl rotate-ca` rotates the Talos API CA and the Kubernetes CA of a running cluster
  (upstream documents a dry-run mode: read `--help` for the default of the version you hold). Not run on this platform. Two things this repository knows that
  upstream's page does not: (1) the new PKI exists only on the nodes and in the new `talosconfig`, **not in the tfstate**, whose
  `talos_machine_secrets` still holds the old one, so the next `tofu apply` would push machine configs carrying the old CA;
  there is no procedure here to carry the new PKI into the state, so do not run an apply on that cluster afterwards until that is solved
  (the first rotation is a lab task: `LAB-CHECKLIST.md`, B13); (2) every kubeconfig, talosconfig and gpg artifact must be reissued afterwards
  (`task kubeconfig`).
- **A leaked kubeconfig or talosconfig** is K1's problem: the file is valid until it expires. Short-lived read access exists
  (`task talosconfig-new`, `os:reader`, 8 h by default) so that the long-lived file is carried less.

### etcd Secrets key (K3) and disk passphrase (K4)

The machine config takes a single value for each (`cluster.secretboxEncryptionSecret`, the `luks2` key slot). Replacing
the value in place leaves existing data under a key the node no longer holds: Secrets unreadable by the apiserver (K3), disks
that do not unlock at the next boot (K4). `upgrade.md` ("The Secrets encryption key (etcd) — not rotatable in place") says the
same for K3; whether Talos can be given a second key was **not verified**. So, for a suspected leak of either:

1. Treat every Secret that was in etcd as leaked if the leaked key was K3 and the attacker also had a snapshot, a disk or the state; K4 and a
   disk image together expose the disk contents. Rotate what the Secrets contain, not only the key (`incident-response.md`, rotation table).
2. Build a new cluster (new `random_bytes` and `random_password`, new Talos PKI), restore OpenBao into it, cut over, destroy the old one.
3. Erase the old state generations, snapshots and artifacts (section 4).

### State passphrase (K5) and artifact passphrase (K6)

OpenTofu's `encryption{}` block supports a key rollover with a `fallback` method: the new key becomes the method used to
write, the old one stays as the fallback to read, one apply re-encrypts the state, and the fallback is then removed. **The block in
`backend.tf` has one method and no fallback today; the rollover is an edit of that file on the operator's machine, and has not been run.** Order:

1. `gen-passphrase.sh` for the new value; keep the old one until step 6.
2. Add the new key provider and method, make it the `state` and `plan` method, put the old one in `fallback`.
3. `tofu apply` (a plan reads the old state through the fallback, the apply writes it under the new key).
4. `task backup-state PROVIDER=<p>`: the replica now holds the new ciphertext as its current object. The dated generations
   (the last five, and any `STATE_LABEL` copy such as `pre-upgrade`) **stay under the old passphrase**.
5. If K6 is not set, the artifacts and snapshots were under K5. The upload trigger of `backup.tf` does **not** include K5 (only a separate K6),
   so a changed K5 re-uploads nothing by itself: re-run the upload with `-replace=terraform_data.backup[0]` in the same apply, take a new
   etcd snapshot (`task etcd-snapshot`), then confirm with `task restore-artifacts`. If K6 is set, rotate it the same way: setting a new K6 does re-upload the artifacts.
6. Delete the old generations, old snapshots and old artifact versions (section 4), remove the fallback, update the CI secret.
   Only then destroy the old passphrase: until the last object under it is gone, the old passphrase still opens it.

### Bastion keys (K9)

Offboarding, certificates, `revoked_keys` and the host-key pin are in `admin-access.md` ("Bastion identity, host key and
Internet egress"). Escrow of the SSH CA private key is the operator's: offline media or OpenBao's SSH secrets engine with the same 8 h maximum
lifetime; this repository operates neither.

### Escrow: how many custodians

Today `docs/admin-access.md` states that OpenAether has **one operator**. A single custodian is a single point of loss, and a single
leak. For anything that matters: the seal key escrow has two custodians at minimum and is proved by a hash and attested in the cluster
(apps `vault/README.md`, Day 0, steps 1 and 5); the recovery shares are one per operator; K5 and K6 belong in two different vaults, each with a
second person able to open it. Where only one person exists, write that down in the incident register rather than leaving it implied.

## 4. End of use, erasure and archive

- **Nothing is erased on schedule.** No bucket in this repository has versioning, a lifecycle rule or an object lock set, and the supply-chain
  page says bucket policies for the state and artifact buckets "are not handled here". So an old state ciphertext stays in its bucket until someone deletes it.
- **To erase an old generation of a key**: list (`task backup-state PROVIDER=<p> -- --list`, and `aws s3 ls` on both stores with
  the endpoint), delete every dated generation and `STATE_LABEL` copy, every old `etcd-*.snap.gpg` and artifact, **every object
  version and delete marker if the bucket is versioned** (a plain delete leaves them), on BOTH stores. Then re-list.
- **`shred` is not an erasure on an SSD** or on a journaled or copy-on-write filesystem: the controller remaps blocks. Keep key material
  on an encrypted volume or in RAM (`mount -t tmpfs`), and treat the destruction of the medium, or of the encryption key of the volume, as the erasure.
- **Archive**: a key is archived only as long as an object under it exists and may have to be read (a retained snapshot, a state
  generation). The archive of K5 is therefore as long as the longest retention of a generation or snapshot (`backup-policy.md`).
- **Decommissioning a cluster**: `cluster-down` leaves the buckets on purpose (deleting the state bucket deletes any possibility of restoring).
  When the cluster is finished for good, empty the buckets (versions included) after the last restore you may need, delete them, revoke K7 and K8,
  and destroy K5 and K6. `backup-policy.md`, "Decommissioning".

## 5. Recorded deviations and residual risks

| Item | What the rule asks | What is here | Why, and what would close it |
|---|---|---|---|
| TLS-12: CA custody | Root key offline, ideally in an HSM; intermediate in an HSM-class device | The offline root's key is in the operator's custody (apps runbook offers a hardware token or offline media; a password manager is the recorded deviation); the intermediate's key lives in OpenBao's raft data, wrapped by the seal key, a software key in a Secret on the same nodes (K11) | Self-contained, hands-free restart. Closing it: a transit or PKCS#11 seal against a separate OpenBao or an HSM outside the cluster. Migration is **untested** and circular if the external seal is inside the cluster it unseals |
| TLS-12: AES-GCM wrap (PA-079 R13 asks for a key-wrap mode) | AES-KW or SIV | The upstream static seal wraps with AES-256-GCM | Owned by upstream; revisit if OpenBao offers a key-wrap mode |
| TLS-12: three CAs | One hierarchy | The OpenBao PKI (offline root), the listener CA `openbao-ca` (self-signed, cert-manager) and the Istio CA (istiod) | The listener CA must exist before OpenBao starts (it signs OpenBao's own certificate), so it cannot live in OpenBao's PKI; the Istio CA is the upstream default. See the apps inventory |
| TLS-19: no post-quantum hybrid | Hybrid key establishment where recorded traffic stays valuable for years | Bastion SSH `KexAlgorithms` is classical (curve25519, DH group 16/18) on Ubuntu 22.04, whose OpenSSH 8.9 does not know `sntrup761x25519`; Cilium WireGuard is classical and cannot be changed; gateway and mesh TLS follow upstream defaults | The admin traffic that matters rides inside TLS and mTLS (Talos API, kube-apiserver, OpenBao) over the SSH tunnel, whose own handshake is also an inner layer: the double wrapping lowers, not removes, the exposure. Closing it: the bastion image on Ubuntu 24.04 with the hybrid KEX first (`bastion_image_id`, replaces the bastion), and the Envoy, ztunnel and Go builds that ship hybrid groups. Whether OpenBao's Go build already negotiates one is **unverified** here. Certificate signatures: SHA-384 for the offline root and intermediate are in the apps runbook; the existing certificates stay as signed |
| DP-17: machine secrets reach new nodes over the unauthenticated maintenance API | Authenticated delivery of keys to the equipment | `first-cluster.md`, "Residual risk: the maintenance-mode apply" | Upstream design; compensated by the private network, the SSH tunnel, the bastion allowlist and (OVH, Outscale) the security group admitting 50000 from the bastion only |
| Shared break-glass SSH account | Individual accountability | `bastion_ssh_keys` stays beside `bastion_admins` | Automation and break-glass; `bastion_require_hardware_key` does not cover it |
| Single operator | Two custodians per escrow | One person | Stated in `admin-access.md`; the attestation of the seal-key escrow requires two holders and says so when it does not |

## 6. Review

Re-read this page with every change that adds a generated key, a secret variable, a bucket or a bastion credential; at each
rotation; after every incident; and at least yearly (`release-checklist.md`, "Quarterly security review", does the quarterly pass and
the yearly one). A row with no period, no impact or no replacement is a defect.
